## WeSwitch v0.6.1

Batch model configuration for Codex Mac. Chinese by default, with an English toggle.
自定义模型终于能在 Codex 选择器里出现了 —— 上一版写入的目录被 Codex 拒收，本版修好。
Fixes the reason custom models never appeared in Codex's model picker.

### Downloads
- Apple Silicon: `WeSwitch-v0.6.1-macos-arm64.zip`. Extract and open WeSwitch.app. Python is bundled, so no Python, Homebrew or WorkBuddy installation is needed; the app opens a local browser UI.
- Intel Mac: use the source archive or `Start WeSwitch.command` with Python 3.11+. No standalone Intel binary is included.

### The bug
Custom models were configured correctly but never showed up in Codex's model picker. Two independent defects were behind it.

1. **No catalog was ever created.** The picker renders the entries of `model_catalog_json`, and a custom model with no catalog entry cannot be selected. WeSwitch only merged into a catalog that already existed, and refused to create one from nothing — deliberately, because a catalog holding only custom models would make the built-in models disappear. On a machine with no catalog yet, the option was therefore disabled and **nothing was reported as wrong**. The configuration was applied, `manifest.json` recorded `"catalog": null`, and the picker had nothing to show.
2. **The generated entry was not one Codex would accept.** `codex-cli` 0.159.2 parses this file with serde and rejects the **entire file** when a single entry omits a required field. Measured against the real binary, `shell_type`, `support_verbosity`, `truncation_policy`, `experimental_supported_tools` and an instructions field are all mandatory. The entry WeSwitch built carried none of them, so it would have been rejected outright — costing every model in the picker, not just the custom one. The old guard against writing a catalog was, in effect, hiding a second and worse bug.

### What changed
- **A first catalog can now be created safely.** When no catalog exists, the merge starts from the models Codex already has: the local `models_cache.json` (a plain file read), or failing that the catalog inside the installed build (`codex debug models --bundled`). Both are read from your own installation; nothing is bundled with this tool. The existing models are carried over byte-for-byte, so the picker's list cannot shrink. Only when neither source can be read is the option still not offered. The preview says which source was used.
- **Generated entries carry exactly the fields Codex requires, and no more.** Only the structural fields are copied from a real entry in your own catalog, so their accepted values track the installed build. Fields that describe the source model's own capability — `context_window`, `max_context_window`, `service_tiers`, `additional_speed_tiers`, `tool_mode` — are deliberately **not** copied: inheriting a 272k context window or a "priority" service tier would be a false claim about a model this tool has never called, and a wrong context window fails real requests rather than merely looking wrong.
- **Nothing is saved until Codex itself has parsed it.** The candidate catalog is written to a throwaway `CODEX_HOME` and re-parsed by the installed Codex before anything reaches `~/.codex`. If Codex would reject it, no file is written and Codex's own error text is shown verbatim, naming the exact missing field.
- **The refusal says which file is at fault.** A hand-made catalog that Codex cannot parse is already unusable, so when that is the cause the message says so, instead of leaving you to conclude the new entry was the problem.

### Verified against the real thing
- Both defects were reproduced first and fixed against `codex-cli` 0.159.2 (`/Applications/ChatGPT.app`), not against a model of it: a catalog written by this version is accepted, still lists all 10 pre-existing models, and adds the custom one as `visibility: "list"`.
- 310 unit/API/localization tests and 288 real-browser assertions passed. The browser suite still proves that switching language preserves every form control node, and audits the English page for zero visible CJK.
- The pre-write validation is covered by regression tests against a stub CLI, so the suite's result does not depend on which Codex build happens to be installed on the machine running it. This was a real trap: the browser suite had been exercising the host's Codex.
- A SHA-256 companion file is published for the app ZIP. Checksums verify file integrity, not publisher identity.

### Limitations
- **This changes the write path**, unlike v0.6.0. If you applied a configuration with v0.6.0 or earlier, the catalog write did not happen (or, in theory, produced a file Codex refused). Re-run WeSwitch with "write model catalog" checked and apply again.
- Once the catalog is written, the picker reads only that file, so later remote catalog updates from Codex no longer take effect. Point `model_catalog_json` back at its original path to restore that; a restore from the UI does this too.
- Validation needs the Codex CLI. Without Codex installed, the check is skipped and the preview says nothing about it rather than pretending it ran.
- No Developer ID signing or Apple notarization. An ad-hoc signature is not a verified publisher identity; Gatekeeper may warn or block launch. Do not disable Gatekeeper globally.
- Listing models is metadata discovery, not a Responses/tool-call compatibility test. A successful connection test still does not prove tool calling, long context or streaming. Restart Codex fully after applying changes.
- Retention does delete backup directories under `~/.codex/model-ui-backups/` once there are more than six. The original configuration is always kept, but intermediate backups are not.
